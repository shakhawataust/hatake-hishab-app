1. The big picture

The single most important thing to understand: the database was never on your laptop. Supabase is a cloud service. Only the web page was local. So "putting this online" does not mean moving data anywhere — it means publishing the web page to a public address.

Why this matters for cost and reliability Because the browser talks to Supabase directly, Vercel only ever hands out fixed files. There is no application server to keep running, patch, or pay for. If Vercel is slow, your data is still safe in Supabase; if you switch hosts, nothing about the data changes.

2. How the production build works, step by step

One command does all of it:

npm run build   # which runs: next build

Here is what happens inside, in order. Steps 2–6 are what Next.js 16 printed during the real build captured for this document.

1

Read the settings

Next.js loads next.config.ts and then reads .env.local, picking up the two NEXT_PUBLIC_* Supabase values. The NEXT_PUBLIC_ prefix is an instruction: bake this value into the browser bundle. Anything without that prefix would stay server-side only.

✓ Running next.config.ts took 670ms
2

Compile and bundle

Turbopack (the new Rust-based bundler in Next.js 16) walks every import starting from layout.tsx, converts TypeScript and JSX into plain JavaScript, compiles the Tailwind CSS, then splits the result into chunks a browser can cache separately.

✓ Compiled successfully in 1553ms
3

Type-check the whole project

A separate pass runs the TypeScript compiler in strict mode. This is a real gate, not a warning: a type error here fails the build and nothing deploys. It is the main reason a broken version cannot silently reach your members.

  Running TypeScript ...
  Finished TypeScript in 946ms ...
4

Collect page data

Next.js inspects each route to decide whether it can be pre-rendered at build time or must wait for a request. It finds two routes — the app itself and the 404 page — and both qualify as static.

5

Pre-render the HTML

The HTML shell is generated once, now, and saved as a file. Because page.tsx is marked "use client", that shell deliberately contains only the loading state — the real screens are drawn by JavaScript in the member's browser after they sign in.

Finalize and report

Assets get content-hashed names for permanent caching, and the route table is printed. The ○ marker on both routes is the key result.

What "○ Static" buys you Both routes are plain files. That is why this app can be hosted free on Vercel, Cloudflare Pages, or Netlify with identical results, and why the first paint does not wait on any server of yours.

4. From build to live URL

deploy.sh automates the four stages below. The build from section 2 happens inside stage 3 — but on Vercel's machines, not yours.

Run it:

cd ~/Documents/hatake-hishab-app
./deploy.sh

The script re-reads .env.local each time and deletes stale Vercel variables before adding new ones, so re-running it is safe and repeatable.

Two manual settings are still required after the first deploy The app will not work for members until both are done in the Supabase dashboard. deploy.sh prints this reminder when it finishes.
  1. Authentication → URL Configuration. Set Site URL to your new address, and add both <your-url>/** and http://localhost:3000/** to Redirect URLs. The sign-up code uses window.location.origin for the confirmation link, so without this, confirmation emails send members to localhost:3000 — which only exists on your Mac.
  2. Authentication → Sign In / Providers → Email. Turn Confirm email off for a small trusted team, or configure SMTP. Supabase's built-in mail service is limited to a few messages per hour and will quietly stop delivering.
Free hosting caveat Vercel's free Hobby tier forbids commercial use. If the farm is a business, either take Vercel Pro or host on Cloudflare Pages or Netlify, whose free tiers permit commercial use. Because the build output is fully static, all three are drop-in equivalents. Supabase's free tier has no such restriction.

5. Design architecture

The design has one governing idea: the browser is the application, and the database enforces the rules. There is no middle tier. This is what makes the app cheap and simple — and it is also why the security model in section 7 has to be airtight.

Why no backend of your own

A conventional app would put a server between browser and database to check permissions. Here, PostgreSQL's Row Level Security does that job inside the database. Fewer moving parts, nothing to run — but it means every rule must be expressed as a database policy, because a determined user can send any request they like straight to Supabase.

Why the two publishable keys are safe

Both NEXT_PUBLIC_* values ship inside the JavaScript bundle and anyone can read them. That is by design. They identify the project; they grant nothing. Access comes from the signed-in user's token, and RLS re-checks it on every single query.

Nine tables. Every farm-scoped table carries a farm_id, which is the column RLS keys off — that single convention is what keeps two farms' data apart.

7. Security model

Because the browser reaches the database directly, the database is the only place rules can be enforced. Four layers do the work:

ControlHow it worksWhy it matters
IdentitySupabase Auth issues a token per signed-in userEvery row records who created it via created_by
IsolationRLS on all 9 tables, gated by is_farm_member(farm_id)One farm cannot read another's data even by crafting a direct request
Privileged actionssecurity definer functions with explicit guardsAdding a member checks admin rights inside the database, not in the UI
FilesPrivate bucket; policy maps the first folder name to a farm_idReceipt images follow the same isolation rule as table rows

The one pattern worth remembering

Every farm-scoped policy is the same shape:

create policy "farm members access transactions" on public.transactions
  for all using (public.is_farm_member(farm_id))
       with check (public.is_farm_member(farm_id));

using filters what you may read; with check validates what you may write. Both call the same function, so reads and writes cannot drift apart. Any new farm-scoped table must copy this pattern — a table with RLS enabled but no policy is invisible to everyone, and a table without RLS is visible to everyone.

The current gap: roles are cosmetic, not enforced RLS separates farms correctly. It does not separate roles — the policies check only that you are a member, not which role you hold. The single role check in the app (farm.role === "admin", at page.tsx:2883) merely hides the member-management form in the interface.

In practice this means a field_member could still read financial figures or write records by talking to Supabase directly, bypassing the UI. For a small trusted family or team this may be acceptable. If it is not, the fix belongs in the RLS policies — not in the React code. invite_farm_member() already shows the right pattern: it verifies admin rights inside the database.

8. Screens and roles

11 screens

Dashboard, Expense, Sales, Harvest, Crop Batches, Orders, Stock, Labor, Investment, Reports, Settings.

All are sections of the same component, switched by a view state value — not separate pages. This is why the build reports only one route.

4 roles

admin, accountant, field_member, sales.

Stored per farm in farm_members, so the same person can hold different roles on different farms. See the caveat in section 7 about enforcement.

3 languages

Bengali (bn, the default), English (en), Japanese (ja).

Screen names come from a labels table keyed by language and view; members switch language in the interface.

Installs like an app

A web manifest, icon, and theme colour were added, so Share → Add to Home Screen gives a real icon that opens fullscreen.

No app store, no review process, no separate Android and iOS builds.

Adding a member — the order is not optional

invite_farm_member() looks the person up in auth.users by email. If they have not signed up, it raises "This email has not created an account yet." So:

  1. Send the member the app URL.
  2. They tap Sign Up with their own email and password.
  3. They tell you which email they used.
  4. You, as admin, add that email from the Settings screen and choose their role.

9. Verification checklist

Already verified for you Production build succeeds · TypeScript passes clean · both routes prerender static · all 9 tables exist in the live database · both database functions execute with working guards · the sales role exists · manifest and icon serve correctly · no secrets committed to Git.

After your first deploy, confirm these in a browser:

  1. The app opens over HTTPS at the Vercel address.
  2. You can sign up a test account and reach the dashboard.
  3. Creating a farm works — you become its Admin.
  4. A record you add on your phone appears on your laptop after refresh. This is the proof that shared, from-anywhere access works.
  5. A second test account not added to the farm sees no farm data. This proves RLS isolation.
  6. Add to Home Screen on a phone opens fullscreen with the icon.

10. Known issues, most important first

1. Roles are not enforced in the database As described in section 7, RLS checks farm membership but not role. Fix in the policies, not the UI. Decide whether this matters for your team before adding members outside the family.
2. One file holds the entire application src/app/page.tsx is 3,050 lines containing all 11 screens, authentication, data loading, calculations, and translations. It works and it builds clean, but every change carries a risk of touching something unrelated, and it is hard to review. Splitting it by screen is the highest-value cleanup available.
3. Supabase's built-in email will not scale Limited to a few messages an hour. Fine while testing; configure SMTP (Resend, Brevo) before onboarding real members, or leave email confirmation off.

4. No offline support

Every screen needs a live connection — the app reads from Supabase on load and writes immediately. In a field with poor signal, entering data will fail rather than queue. If members work in low-coverage areas, offline queueing is worth adding; if they enter data at home, it is not.

5. Free tier is not licensed for commercial use on Vercel

See section 4. Cloudflare Pages and Netlify are drop-in alternatives whose free tiers allow it.
